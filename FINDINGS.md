# Findings: Pydantic AI Harness under durable execution

Measured 2026-10-01 against `pydantic/pydantic-ai` at `dac0464` (main), on one Apple M4, with
Temporal (local dev server), DBOS (SQLite) and Prefect (`prefect_test_harness`). Every number
below is regenerated by the scripts in `suite/`; the full table is [`results/GRID.md`](results/GRID.md).

## The instrument, and why its verdicts are admissible

Each case is one harness capability on an agent driven by a deterministic `FunctionModel`,
run twice per engine: once with only a `ping` tool (hooks), once calling every tool the
capability contributes (tools). Temporal runs with `max_cached_workflows=0`, so every
workflow task replays history from the start.

A side effect counts when it happens in code the engine re-executes on recovery: Temporal
workflow code, a DBOS workflow outside a step, a Prefect flow outside a task. It is caught by
a `sys.addaudithook` (sockets, subprocesses, file writes) plus a probe on `loop.getaddrinfo`,
which runs in the caller's task, and attributed to the innermost capability frame. Events
whose innermost frame belongs to the engine itself (Prefect creating its storage directory
inside a flow) are the engine's bookkeeping and do not count. The grid never leaves the
machine: the audit hook refuses every non-local connection, and integrations get fake tokens.

**Controls.** Two probe capabilities write a line to a file after each model request: one in
the hook body, one through `@durable_operation`. In every engine column the first reads
BROKEN (Temporal: the sandbox refuses the write, SANDBOX) and the second SAFE. Twice during
development a harness change silently flipped the unprotected control to SAFE; both times the
control caught it before any result was reported.

**Recovery, demonstrated rather than inferred** (`suite/dbos_recovery.py`): run a DBOS workflow,
then fork it after its last recorded step, which is what recovery of a committed run does.

| Case | file writes, first run | repeated on recovery |
|---|---|---|
| Control: write in hook | 2 | **+2** |
| Control: write via `@durable_operation` | 2 | **+0** |
| `CapabilityCreation` (shipped) | 5 (the module and its manifest) | **+5** |

|---|---|---|---|---|---|

Rows include the two controls and seven `[id]` variants. No capability's **hooks** do
workflow-side I/O on any engine. Every defect below is in a capability's **tools** or its
**construction**.

## New: no open issue found

1. **`Capability(instructions=...)` cannot be used with Temporal or Prefect.** It has no tools,
   yet contributes an empty `FunctionToolset` with `id=None`, which both engines refuse at
   construction. DBOS accepts it. `Researcher` hits this through its own
   `Capability(instructions=...)`, so it stays broken even with every harness toolset given an
   id. #9233 explicitly keeps user-configured capabilities at `id=None`, so it does not cover
   this; the natural fix is for a capability to contribute no toolset when it has no tools.

   ```python
   Agent(model, capabilities=[Capability(instructions='Be brief.'), TemporalDurability()])
   # UserError: Toolsets that are 'leaves' ... need to have a unique `id`
   ```

2. **On DBOS, seven harness capabilities do raw I/O in workflow code.** DBOS wraps only MCP and
   dynamic toolsets; function tools run in the workflow, and the documented remedy is to
   decorate I/O tools with `@DBOS.step`, which a user cannot do to a shipped tool. On recovery
   each of these runs again:

   | Capability | Repeats on recovery | Where |
   |---|---|---|
   | `ExaSearch`, `ExaAgent` | paid Exa API calls | `exa/_toolset.py:191, 234`, `exa/_agent.py:176` |
   | `YouSearch`, `YouResearch` | paid You.com API calls | `youdotcom/_toolset.py:329, 379`, `_research.py:139, 165, 191` |
   | `LocalStack` | AWS CLI commands, temp files, health check | `localstack/_toolset.py:297, 298, 356` |
   | `CapabilityCreation`, `RuntimeAuthoring` | writing model-authored modules and the manifest | `capability_creation/_store.py:69, 71, 100, 102` |

   `FileSystem` and `Shell` are SAFE on DBOS because their I/O goes through the durable
   workspace, so the pattern to follow already exists in the harness.

3. **`ExaSearch` and `ExaAgent` cannot be constructed inside Temporal's workflow sandbox**
   (`RestrictedWorkflowAccessError` on `http.client`) unless `exa_py` is added to the
   passthrough modules. With it they are SAFE. Not documented. `YouSearch` needs nothing.

4. **`PydanticAIDocs` registers its toolset at run time**, which Temporal and Prefect refuse
   ("cannot be added at runtime") even once it has an id.

## Already known: confirmed, not claimed

- **#9233** (dsfaccini): harness capabilities whose toolsets carry no `id`. The grid confirms it
  across engines: 12 capabilities cannot be constructed with `TemporalDurability` or
  `PrefectDurability`, and passing `id=` does not help, because the id never reaches the
  toolset. The local branch `fix/harness-leaf-toolset-ids` (stashed in `upstream/`) shows the
  fix turns 6 of them SAFE on Temporal (8 with `exa_py` passed through) and 8 on Prefect, but #9233 already has two closed
  outside PRs and an earlier harness PR, so it is not ours to send.
- **#8927**: `SubAgents` with `agent_folders` fails under Temporal. The configuration the docs
  prescribe, `SubAgents(include_self=True, agent_folders=None)`, is SAFE on all three engines.
- `TrajectoryJudge` (#8988, PR #9328) and `PlaywrightBrowser` refuse durable execution by
  design and say so.

## Not run, and why

15 capabilities per engine need a real external service: 11 MCP integrations (GitHub,
Slack, Linear, Notion, ...) and four remote sandboxes (E2B, Modal, Sprites, SSH). For the MCP
ones the audit still shows their connections come from activities, steps or tasks, never
from workflow code, so their hooks are clean; their tools are untested. `Macroscope` needs
its CLI on `PATH`.

## Limits

- One workload per mode: `ping`, then each tool once with the smallest schema-valid arguments.
  A capability whose defect needs a specific argument or a long run is not exercised.
- The audit sees sockets, name lookups, subprocesses and file writes. It does not see
  non-determinism without I/O (a `uuid4()` or `random` value in workflow code feeding a later
  durable unit); Temporal's sandbox catches some of that, DBOS and Prefect do not.
- AWS Lambda durability is not covered yet.
- The DBOS recovery demonstration covers `CapabilityCreation`; the other six DBOS rows are
  audit results, not yet demonstrated by recovery.
